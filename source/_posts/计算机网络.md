## `POST` 和 `GET` 是什么区别？
POST 和 GET 是 HTTP 协议中用于客户端与服务器之间进行数据交互的两种主要方法，它们之间有以下区别：

**1. 传输方式：** 
   - **GET：** 将参数附加在请求的 URL 后面，以查询字符串的形式传递给服务器。数据以键值对的形式显示在 URL 中，例如：`http://example.com/page?name=value&age=25`
   - **POST：** 将参数包含在请求体中，而不是在 URL 中。数据以请求体的形式传递给服务器，对用户来说不可见。  

**2. 数据长度：** 
   - **GET：** 由于数据附加在 URL 中，对传输的数据量有限制。在实际使用中，受到浏览器和服务器的限制，通常不适合传输大量数据。
   - **POST：** 数据放在请求体中，可以传递大量数据，理论上没有大小限制。  

**3. 安全性：** 
   - **GET：** 参数在 URL 中可见，不适合传输敏感信息，因为信息可能会被记录在服务器的访问日志中，同时也可能被浏览器缓存，有一定的安全风险。
   - **POST：** 参数在请求体中，相对于 GET 更安全，适合传输敏感信息，例如登录凭证等。  

**4. 幂等性：** 
   - **GET：** 对相同的请求，多次执行不会产生不同的结果。因此，GET 操作是幂等的，不会对服务器状态产生影响。
   - **POST：** POST 操作不一定是幂等的。多次执行相同的 POST 请求可能会对服务器状态产生不同的影响，例如重复提交表单可能导致多次记录。  

**5. 缓存：** 
   - **GET：** 可以被缓存，可以被浏览器缓存，可以被代理服务器缓存。
   - **POST：** 默认情况下不会被缓存，需要使用特定的缓存控制头。  

总的来说，GET 适用于传输小量数据，对安全性要求较低的场景，而 POST 适用于传输大量数据，对安全性要求较高的场景。在实际应用中，选择使用 GET 还是 POST 取决于具体的业务需求。  

## TCP和UDP的区别？

- TCP是面向连接的，UDP是无连接的
- TCP是可靠的，UDP是不可靠的
- TCP是面向字节流的，UDP是面向数据报文的
- TCP只支持点对点通信，UDP支持一对一，一对多，多对多
- TCP报文首部20个字节，UDP首部8个字节
- TCP有拥塞控制机制，UDP没有
- TCP协议下双方发送接受缓冲区都有，UDP并无实际意义上的发送缓冲区，但是存在接受缓冲区  

## TCP为什么三次握手而不是两次？
TCP（Transmission Control Protocol）使用三次握手来建立连接的原因主要是为了确保双方都能够正确地同步初始化序列号（Sequence Number）和确认序列号（Acknowledgment Number）。这三次握手的步骤如下：  

**1. 第一次握手（SYN）：** 
   - 客户端向服务器发送一个带有SYN（同步）标志的数据包，表示客户端请求建立连接。同时，客户端选择一个初始序列号（ISN）。  

**2. 第二次握手（SYN + ACK）：** 
   - 服务器接收到客户端的SYN请求后，会回复一个带有SYN和ACK（确认）标志的数据包，表示确认收到客户端的请求，并同样选择一个初始序列号。  

**3. 第三次握手（ACK）：** 
   - 客户端收到服务器的确认后，再次发送一个带有ACK标志的数据包，表示客户端确认收到了服务器的确认。这个ACK标志的数据包不包含任何数据。  

这样的三次握手机制有几个关键的原因：

- **避免已失效的连接请求导致资源浪费：** 
    - 如果只有两次握手，那么如果客户端发送的连接请求由于某种原因在网络中滞留，而服务器已经创建了连接并分配了资源，这时客户端重新发起连接请求，服务器会认为这是一个新的连接，而实际上可能是之前已经失效的连接。通过第三次握手，可以确保客户端和服务器都已经确认连接的建立，避免了这种情况。
    
- **防止过早打开连接：** 
    - 如果只有两次握手，可能导致在一些特殊情况下，服务器打开了连接，但客户端并没有真正准备好发送数据。通过第三次握手，可以确保双方都已经准备好并同步好了初始序列号，可以开始可靠地传输数据。

- **解决网络延迟问题：** 
    - 在三次握手的过程中，双方都有机会向对方发送信息，如果其中一方出现网络延迟，可以在握手的过程中及时发现并进行处理。

总体而言，三次握手的设计使得TCP连接的建立更加稳健和可靠，确保了双方都已经同步好了连接参数再开始数据传输。  

## TCP的四次挥手？
TCP的四次握手是TCP连接建立和断开的标准过程，其步骤如下：  
1. 第一次挥手（客户端主动关闭连接）。客户端发送一个`FIN` 报文，表示它准备断开连接，并指定一个序列号`seq` 。此时，客户端进入`FIN_WAIT_1` 状态。  
2. 第二次挥手（服务器确认并进入半关闭状态）。服务器收到`FIN` 报文后，会发送一个`ACK` 报文，确认收到客户端的`FIN` 报文，并指定一个确认序列号`ack` ，其值为`seq` 加1。服务器进入`CLOSE_WAIT` 状态，此时进入半关闭状态，即服务器可以继续发送数据，但客户端不再接收。  
3. 第三次挥手（服务器主动关闭连接）。服务器完成数据传输后，它会发送一个`FIN` 报文，表示它准备断开连接，并指定一个序列号`seq` 。此时，服务器进入`LAST_ACK` 状态。  
4. 第四次挥手（客户端确认并进入时间等待状态）。客户端收到服务器的`FIN` 报文后，会发送一个`ACK` 报文，确认收到服务器的`FIN` 报文，并指定一个确认序列号`ack` ，其值为`seq` 加1。客户端进入`TIME_WAIT` 状态，等待`2MSL（最大报文段寿命）` 时间，以确保服务器已经收到`ACK` 报文，之后客户端进入`CLOSED` 状态。  

这个过程中的每个步骤都是为了确保双方都能正确地关闭连接，避免数据丢失。
